# Resilient profile refresh (FansAPI take-home)

Laravel 13 app that refreshes OnlyFans profile data through Redis queues under
Horizon, validates every upstream response before writing, and never lets a
response it cannot validate destroy the last good data.

Live retrieval works. The reproduction of the original bug works and is
rerunnable. Every number below is from `evidence/`, regenerated by
`scripts/capture-evidence.sh` on this machine.

- [CALL_GUIDE.md](CALL_GUIDE.md) - the demo sequence, file map and Q&A
- [AI.md](AI.md) - what AI was used for, what was checked, what was got wrong
- [REQUIREMENTS.md](REQUIREMENTS.md) - every requested behaviour and where to find it
- `evidence/` - transcripts with commands, exit statuses and elapsed times

## Setup

Docker is the only requirement. No host PHP, Composer or Node.

```bash
cp .env.example .env          # then put your own OFAPI_TOKEN in .env
docker compose up -d          # builds, installs, migrates, builds assets
docker compose exec app php artisan fans:demo seed
```

| What | Where |
| --- | --- |
| App | http://127.0.0.1:8000 |
| Horizon | http://127.0.0.1:8000/horizon |
| Fixture upstream | http://localhost:9000 (private, test only) |

Everything else:

```bash
docker compose exec app ./vendor/bin/phpunit          # 59 tests
docker compose exec app php artisan fans:demo broken  # the incident, rerun (exits 1)
docker compose exec app php artisan fans:demo fixed   # same inputs, fixed
docker compose exec app php artisan fans:demo workload --mode=fixed
docker compose exec app php artisan fans:demo dlq-demo
docker compose exec app php artisan fans:memory --jobs=100
docker compose exec app php artisan fans:demo live    # the only live call
./scripts/capture-evidence.sh                         # regenerate evidence/
```

`.env` is git-ignored and `.env.example` ships with a blank token. No
credential is in this repository, in the evidence, or in the logs.

## Live retrieval: it works

```
GET https://app.onlyfansapi.com/api/profiles/madison420ivy?fresh=true
HTTP 200, 4,448 bytes
```

Verified twice: once with plain `curl` before any code existed, and once end to
end through a queued job and a real Horizon worker
(`evidence/live-retrieval.json`).

| Field | Value |
| --- | --- |
| Upstream id | 5140520 |
| `favoritedCount` (stored as likes) | 605,782 |
| `favoritesCount` (retained, not used as likes) | 16 |
| Subscriber count | not exposed by this endpoint, stays null |
| Upstream revision | not exposed by this endpoint, stays null |
| Served from provider cache | no (`fresh=true`) |

**This uses a managed provider**, `app.onlyfansapi.com`. It owns request
signing and session maintenance; none of that is implemented here.

The reviewer's follow-up said to treat OnlyFans as the upstream HTTP source,
that no OnlyFans account is needed, and that fixtures for the failure modes
plus a live happy-path check are fine. So the direct route was probed as well,
anonymously, from this machine:

| Route | Result |
| --- | --- |
| `GET https://onlyfans.com/api2/v2/users/madison420ivy` | HTTP 400, `{"error":{"code":0,"message":"Something went wrong."}}` |
| `GET https://onlyfans.com/madison420ivy` | HTTP 200, a 17 KB JavaScript app shell with no profile fields in it |

Direct JSON access needs the signed `app-token` / `sign` / `time` headers that
the scraper projects reverse-engineer from OnlyFans' dynamic rules, and the
HTML page renders client-side. Neither gives anonymous profile data, which is
why the managed provider is the live adapter. A direct adapter would slot in
behind the same `ProfileClient` interface once signing exists; the rest of the
pipeline is unchanged by where the JSON comes from.

**`favoritedCount` versus `favoritesCount`.** The first is 605,782 and the
second is 16 for this profile, which is only consistent with the first being
likes received and the second being profiles this account favourited. Both are
kept in the snapshot. This has not been confirmed with the provider.

**No invented revision for live data.** The provider returns no version field,
so none is synthesised from timestamps, hashes or request order. Revision
ordering is proven against fixtures, which do have revisions. Live refreshes
rely on the per-profile lease and run idempotency instead, and record the
provider's own cache provenance so a cached read is never presented as a fresh
upstream fetch.

## The bug, reproduced

The pre-fix handler read only a top-level `likes`, defaulted a missing value to
zero, and treated every response as successful. It is quarantined in
`app/Demo/` and reachable only through `fans:demo broken`.

`evidence/reproduction-broken.txt`, exit status 1 by design:

| Case | Stored likes | Stored revision | Marked successful |
| --- | --- | --- | --- |
| New nested format | **0** | 9 | yes |
| Old top-level format | 120000 | **9**, never advanced | yes |
| 429, no `Retry-After` | **0** | 9 | yes |
| 500, empty body | **0** | 9 | yes |

`evidence/reproduction-fixed.txt`, exit status 0, identical inputs:

| Case | Stored likes | Stored revision | Last success |
| --- | --- | --- | --- |
| New nested format | 121000 | 11 | advanced |
| Old top-level format | 120000 | 10 | advanced |
| 429, no `Retry-After` | 120000 | 9 | **untouched** |
| 500, empty body | 120000 | 9 | **untouched** |

There was no deployment on our side. The upstream contract moved, and the
handler's assumptions stopped being true. Completed queue jobs are not evidence
of a valid refresh, which is exactly why monitoring stayed green.

## What a response must prove

| Rule | Behaviour |
| --- | --- |
| Accepted shapes | `{"likes":N,"revision":R}`, `{"profile":{"likes":N},"revision":R}`, and the provider's `data.favoritedCount` |
| Missing likes | invalid response, nothing is written |
| Explicit zero | valid data, written |
| Negative, fractional, boolean, null, non-numeric, overflowing | rejected |
| Numeric strings | accepted only in canonical form (`"0"`, `"121000"`); no sign, whitespace, leading zero, exponent or decimal point |
| Both locations present and disagreeing | rejected |
| Equal revision, different content | rejected |
| Equal revision, identical content | recorded once as `verified_unchanged`, counted separately from a data update |
| Older revision than accepted | `stale_response_ignored`, nothing written, no success recorded |
| Identity mismatch | rejected; upstream id uniqueness is enforced by a SQL index |

Every rejection preserves the entire last valid snapshot and leaves
`last_success_at` alone. The write is one short transaction that re-reads the
accepted revision under `SELECT ... FOR UPDATE`, so queue delivery order cannot
decide which value survives. `tests/Feature/ConcurrentCommitTest.php` proves
that across two real processes and two MySQL connections.

Scheduling: above 100,000 likes, refresh 24 hours after success; at or below,
72 hours. Exactly 100,000 gets 72 hours. All UTC, all tested.

## Queues, retries and account isolation

Actual configured values (`config/fansapi.php`, `config/horizon.php`,
`config/queue.php`):

| Setting | Value |
| --- | --- |
| HTTP connect / total timeout | 3s / 10s |
| Job timeout | 20s |
| Horizon supervisor timeout | 30s |
| Redis `retry_after` | 60s |
| Per-profile overlap lease | 45s, ownership-safe release |
| Worker container stop grace | 45s |
| Upstream requests per logical run | 5 |
| Queue delivery guard | 100 |
| Logical refresh deadline | 5 minutes |

The ordering matters: **20s job < 30s supervisor < 60s reservation**. A normal
attempt can never have its Redis reservation expire underneath it, and a hung
attempt is killed long before a second worker could pick it up. The job's own
`$timeout` overrides the ordinary worker timeout, which is why both are stated.

Three counters are tracked separately because the framework conflates them: a
release consumes a queue attempt without making an HTTP request. So the delivery
guard is a generous framework backstop, while the real limits are a persisted
deadline and a separately counted HTTP budget, both enforced in `handle()`.
`retryUntil()` is deliberately not defined, because defining it makes Laravel
stop enforcing `$tries` entirely.

| Outcome | Policy |
| --- | --- |
| 429 with usable `Retry-After` | seconds or HTTP-date, respected exactly, never shortened |
| 429 without one | randomised delay plus an account cooldown |
| Timeout, network error, 5xx | bounded exponential backoff with jitter, capped at 20s |
| 401, 404 | terminal, data preserved |
| 403 | own category, never read as "profile deleted" |
| Invalid 2xx payload | schema failure, quarantined in the dead-letter queue |

Jobs are released, never slept on, so a waiting profile does not hold a worker.
The HTTP client performs no retries of its own, so queue retries and client
retries cannot multiply.

**Isolation.** One reserved Horizon process per account (`refresh-a`,
`refresh-b`), fixed at two workers total, plus an account cooldown so a
throttled account stops hammering the upstream. Queue priority alone would not
give fairness. The honest limit: the provider bills one quota per *workspace*,
shared by every key, and cached reads consume it too, so a separate workspace
gate exists and applies to provider-backed accounts. Account isolation cannot
guarantee successful requests when a shared workspace budget is exhausted.

## Workload results

12 account A profiles and 4 account B profiles, all seeded at 120000 likes,
revision 9. A's burst at t=0; B at t=1, 4, 7, 10. A is throttled with 429s and
no `Retry-After` for 15 seconds with 2-second responses throughout, then
returns the nested format at revision 11; one A profile also gets a single
empty 500 after the outage. B returns valid old-format data at revision 10 in
about 50 ms the whole time. Identical inputs in both modes; capacity is two
workers in both.

**Broken** (`evidence/workload-broken.txt`), two workers sharing one FIFO queue:

| Account | Runs | Valid refreshes | False successes | Peak oldest wait |
| --- | --- | --- | --- | --- |
| A | 12 | 0 | 12 | 11s |
| B | 4 | 0 | 4 | 10s |

All 12 A profiles were overwritten with 0. B's likes survived only because the
old format still happened to parse, and its revision never advanced past 9.

**Fixed** (`evidence/workload-fixed.txt`), one reserved worker per account:

| Account | Runs | Valid refreshes | Upstream requests | Requests per valid refresh | Retries scheduled | Dead letters | Peak oldest wait |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A | 12 | 12 | 15 | 1.25 | 27 | 0 | 52s |
| B | 4 | 4 | 4 | 1.00 | 0 | 0 | **3s** |

B keeps recording valid refreshes while A is failing, and A fully recovers once
the outage ends: all 12 profiles end at 121000, revision 11, and all 4 B
profiles at 120500, revision 10. The healthy account's peak observed waiting age
drops from 10s to 3s purely from reserving its worker. Run-to-run noise on this
machine is a second or two; the earlier capture showed 11s against 0s.

Waiting age is measured from the original enqueue time and survives every
release; it is never inferred from a delayed job's next-ready timestamp. Ready,
delayed and reserved depths are reported separately.

## Dead letters and replay

The dead-letter queue is Laravel's own durable `failed_jobs` table, linked to
the refresh run that produced it. No second broker, no Redis dead queue that
something has to keep draining. A terminal failure inside a worker is handed to
Laravel's failure pipeline, so Horizon's Failed Jobs view and the app's
dead-letter view describe the same thing.

`queue:retry` republishes the work and deletes the failure record, which throws
away the audit trail. Replay here is a small domain action instead: it creates
a new linked run through the ordinary dispatch and admission path, the original
stays dead-lettered, and it is marked resolved only when the replay actually
finishes. A concurrent second replay request creates nothing.

`evidence/dlq-demo.txt` runs the whole cycle: permanent throttling exhausts the
5-request budget after 10 queue deliveries, the run is dead-lettered with the
profile's 120000 intact and `last_success_at` never set, the fixture is
repaired, one replay is queued, a duplicate request is refused, and the replay
commits 121000 at revision 11.

## Memory

Design: jobs carry a single integer, the response body is capped at 1 MiB while
it is still arriving (checking after `->json()` would be too late), the body is
decoded once, scheduling queries read only scheduling columns in batches of at
most 100, list pages show 25 rows, and no profile media is ever downloaded.
There is exactly one size limit and it is enforced on the wire.

100 fixture refreshes through one persistent worker after warm-up, mixing
normal responses, ~900 KB near-limit responses and failures
(`evidence/memory.txt`):

| Measure | Value |
| --- | --- |
| Worker PIDs (restarts) | 1 |
| Jobs measured after warm-up | 120 |
| PHP peak allocation | 18 MiB |
| Worker RSS | 73.1 MiB |
| RSS drift, first quarter to last | +0.00 MiB |
| PHP `memory_limit` | 128M |
| Horizon worker recycle threshold | 96 MiB |

The point is the plateau, not the cap: RSS is flat across the run, so memory is
not growing with job count. Sampling happens inside the worker
(`/proc/self/statm` plus PHP's own counters); `memory_reset_peak_usage()` gives
a per-attempt peak and resets a statistic, not memory. Compose-level usage is
recorded separately in `evidence/compose-usage.txt`; the Horizon container's
320 MiB covers a master plus four worker processes, which is why per-worker RSS
is the number quoted here.

## How the code is laid out

Ordinary Laravel, on purpose. Queue jobs, Eloquent models with casts and
factories, a backed enum for run status, event listeners registered in the
service provider, artisan commands on the scheduler, form posts with CSRF,
Blade views, PHPUnit with `RefreshDatabase`. No custom event bus, repository
layer or workflow engine.

| Layer | Where |
| --- | --- |
| Entry points | `routes/web.php`, `routes/console.php`, `app/Console/Commands/` |
| Queue job | `app/Jobs/RefreshProfileJob.php` |
| Domain services | `app/Refresh/` (dispatcher, clients, normalizer, writer, recorder, dead letters, admission, stats) |
| Models and enum | `app/Models/`, `app/Enums/RunStatus.php` |
| Listeners | `app/Listeners/` (dead-letter linking, memory probe) |
| Demo-only code | `app/Demo/` (the broken handler, workload, seed data) |
| Fixture upstream | `fixture-server/router.php` |
| Tests | `tests/Unit/`, `tests/Feature/`, factories in `database/factories/` |

## Interface

Blade and Tailwind, local-only, no SPA. A per-account activity panel polling a
single aggregate endpoint every 3 seconds with an updated-at indicator, a
profile list with search through Scout's database engine, queued-refresh
actions that only enqueue, and a dead-letter list with replay. Escaped output,
POST with CSRF for every change, and backend deduplication so a double click
cannot create two runs. The header shows a LIVE or FIXTURE badge.

Horizon is the operational view for supervisors, process counts, queue depths,
throughput and failed jobs. Jobs are tagged `run:<id>`, with no secrets in tags.
The panel separates queue completions from accepted refreshes and surfaces
stale processing leases, so a crashed attempt does not look busy forever.

Exercised in a real browser with Playwright as well (`evidence/browser-run.txt`):
queue a refresh, the double-click dedupe, search, the retrying profile still
showing its last valid likes, and a dead letter replayed to a valid commit,
with zero console errors.

Logs are structured and connect account, profile, run, queue job and attempt
ids, with distinct events for `request_failed`, `retry_scheduled`,
`refresh_accepted`, `stale_response_ignored` and `dead_lettered`. Authorization
headers, tokens, cookies, the provider's credit balance and full upstream error
bodies are never logged.

## Production plan

**First 15 minutes.** Protect writes before diagnosing: confirm the last good
values are still stored and stop anything that could overwrite them. Then look
at the upstream response shape and status codes, correlate failures by account
and by queue age, and separate an account-level limit from a workspace-level
one. Preserve the evidence, and keep the healthy accounts moving.

**Rollout.** Regression tests first, then a small canary on a few profiles, a
safe worker restart, then widen while watching valid refreshes (not completed
jobs), stored values and revisions, retries per success, and backlog age.

**Rollback.** Trigger on integrity regressions (accepted values moving in ways
the upstream does not justify, revisions going backwards, a jump in
`schema_failure`) or operational ones (backlog age climbing, retries per
success climbing, dead letters appearing). Fall back to a write-disabled mode
or the previous known-good validator. Never back to the zero-overwrite handler.

**Recovery.** Verify stored data per account, confirm backlog age is falling
and retries are bounded, then re-fetch the corrupted records from the upstream.
Do not reconstruct previous values by guessing.

## Scaling

50 million jobs a day is about 579 per second *on average*. That is an
arrival-rate estimate, not proof of capacity. What actually decides it: peak
arrival rate versus average, the service-time distribution (a 2-second upstream
response is a very different machine than a 50 ms one), permitted concurrency
per account and per workspace, retry amplification, database write and history
growth, Redis throughput, and how concentrated the biggest accounts are.

The first limit in this implementation is upstream quota and network-bound
worker capacity: a worker spends nearly all its wall-clock time waiting on the
provider. The evidence to confirm it is requests per valid refresh, the ratio of
`throttled` outcomes to successes, and worker time spent in HTTP versus in the
database. After that, SQL write volume and the growth of the runs and attempts
tables.

Changes should follow those measurements: account and workspace admission with
fair shared pools where quota binds; more workers only where permitted
concurrency actually exists, since adding workers against a fixed quota just
converts capacity into 429s; retention and write optimisation where SQL binds.
One dedicated worker per account is a two-account demo, not a production plan
for many accounts; that becomes weighted shared pools with per-account
admission. Horizon documents no Redis Cluster compatibility, so "enable Cluster"
is not a scaling answer.

## Time spent and what is not done

Roughly 3.5 hours of machine-assisted work end to end, including setup,
the live verification, debugging and the write-up.

Not done, deliberately: no REST API, no SPA, no media downloads, no external
search service, no production infrastructure, no direct OnlyFans adapter. Not
proven: the provider's own failure modes under real load, crash semantics
beyond the commit boundary, and anything about scale beyond this one machine.
`AI.md` lists what remains unverified.
